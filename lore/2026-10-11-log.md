## 2026-10-11 10:25 — SPEC requirements: decisions so far

- Starting SPEC.md / SPEC_impl.md, derived from an external "MCP agent control" implementation plan (OpenAI Secure MCP
  Tunnel -> stdio MCP adapter -> durable supervisor -> Codex app-server). Agreeing on top-level requirements one
  question at a time before writing the files.
- HARD requirement from the user: granting an agent access is the security equivalent of handing over an SSH key. Once
  you have access you have access; security relies entirely on the OpenAI tunnel and the authenticated MCP flow. No
  ports or other ways in beyond what the tunnel needs. No agent may weaken this without extremely explicit user
  confirmation. This directly reverses the plan's "tunnel access is not authorization" stance, so its per-call policy,
  project allowlist, and approval route are dropped.
- Capability: Codex jobs only for now, but the design must assume other agents (e.g. Claude) are added almost
  immediately. Agent-specific assumptions live only in clearly agent-specific code and in SPEC_impl.md, not SPEC.md.
  No premature generalization beyond that.
- Permissions: launched agents always run with full access and no approvals (Codex `--yolo`, Claude
  `--dangerously-skip-permissions`, or each agent's equivalent).
- Sessions: the MCP caller must be able to resume past sessions so context is not lost between invocations. Sessions
  are explicitly created, resumed, and removed, and are not 1:1 with agent turns.
- Transcript access: the calling agent must be able to ask the launched agent to analyze its own transcript, and must be
  able to extract raw transcript ranges directly. Intent: it should feel like talking to the real agent, not like being
  one relay away from it.
- Open: whether a separate long-lived supervisor (with a 0600 Unix socket) is needed for work to survive adapter
  restarts.
- Next: settle the supervisor/IPC question, then the remaining top-level questions.

## 2026-10-11 10:40 — SPEC requirements: remaining top-level decisions

- No survival of in-flight turns across death of the stdio MCP process: keep it simple, no supervisor, no Unix socket,
  zero IPC. Sessions on disk stay resumable. Checked tunnel-client source (commit b91e6c9, 2026-10-09): one long-lived
  stdio child shared by all requests; it is replaced on tunnel-client restart, pipe errors, and some deadline paths
  (e.g. slow `initialize`), and must be re-initialized afterwards. Not per request, not on relay reconnect.
- Working directory: any absolute path. If the caller gives none, use a standard default of some prefix plus the session
  name. Sessions are named; names are limited to lowercase letters, digits, `_` and `-`.
- Codex interface: `codex exec --json` plus `exec resume`, not app-server. Consequence: no mid-turn steering and no live
  clarifying questions; follow-ups are new turns in the same session.
- Client: OpenAI Secure MCP Tunnel only. ChatGPT Dots (always-on ChatGPT agents announced at OpenAI DevDay 2026-09-29)
  are the motivating client; other OpenAI tunnel clients should work but are not specifically targeted.
- File split: SPEC.md is normative, agent-agnostic product behavior including the hard security requirement.
  SPEC_impl.md holds Rust, MCP SDK, storage, process model, and per-agent adapters. AGENTS.md mandates keeping code
  and both specs in sync and forbids weakening the security requirement without explicit user confirmation.
- Next: present the consolidated requirement list for agreement before writing the files.

## 2026-10-11 10:48 — Specs PR opened; primordial prototype and test flow built

- Specs landed as draft PR #7 (bookmark `pr/specs`, base `pr/work-log`): https://github.com/scode/devbox-mcp/pull/7
- Prototype: one MCP tool, `run_turn`, that runs a single Codex turn (fresh session) and blocks until it ends,
  returning the final reply. Deliberately not spec-shaped yet; SPEC_impl.md's status section lists the gaps.
  Dependencies: rmcp 3.5.1 with only `server`, `macros`, `transport-io` (client features only in dev-dependencies).
- Bug found by the shutdown test: tunnel-client stops its child by closing stdin and sending SIGTERM
  (`stdio_command.go`, `stop`). With SIGTERM's default disposition devbox-mcp died without cleanup and the agent's
  background commands survived. Fixed by catching SIGTERM/SIGINT and returning from main, which drops in-flight calls
  and their process-group guards. Verified the test fails without the handler.
- LESSON: rmcp's `TokioChildProcess` client does not reliably close the server's stdin on shutdown; it waits 3 s and
  then SIGKILLs. Tests that need tunnel-client's exact stop behavior must drive the server over raw pipes.
- LESSON: parent-death signal is per spawning thread, so devbox-mcp uses a current-thread tokio runtime.
- NOTE: tunnel-client requests its own shutdown when its stdio child exits.
- NOTE: `Implementation::from_build_env()` in rmcp reports rmcp's own name/version (the `env!` expands in rmcp).
- Test flow (docs/testing.md): (1) `cargo test`, hermetic, fake Codex shell script, real binary over stdio; (2)
  `examples/mcp-call.rs` driver for direct tool calls against real Codex; (3) nested `claude -p --mcp-config ...
  --strict-mcp-config` so a real model acts as the MCP client; (4) the real tunnel, user-only. Layers 2 and 3 were run
  for real: Codex answered "hello world" in about 9 s via the driver, and a nested Claude session called `run_turn` and
  reported all result fields correctly. Layer 4 not run.

## 2026-10-11 11:29 — Adversarial review of PRs #8 and #9, fixes

- Tunnel tests committed as draft PR #9 (bookmark `pr/tunnel-tests`): https://github.com/scode/devbox-mcp/pull/9
- User asked for an adversarial review by a GPT-6.1 high agent: ran `codex exec -m gpt-6.1-sol -c
  model_reasoning_effort="high"`. NOTE: codex's read-only sandbox fails on this machine (`bwrap: loopback: Failed

  (no .git/.jj) so it could not touch the real checkout.
- 11 findings; all accepted. Confirmed the most important with real Codex: Codex runs shell commands in a new session,
  so `bash -c "sleep 303 & sleep 120"` survived devbox-mcp shutdown (group kill misses it); and SIGTERM with stdin open
  left devbox-mcp hanging forever (tokio runtime drop waits on the blocking stdin read).
- Fixes (new PR on top of #9 rather than rewriting #8/#9, since #9 restructured the tests #8 introduced):
  `src/process.rs` kills the agent's whole tree via a /proc walk (SIGSTOP all until stable, then SIGKILL) on drop;
  turn ends on agent exit, not pipe EOF, with a 2 s shared drain deadline; prompt written concurrently with draining;
  tool handler races its turn against rmcp's cancellation token (rmcp does not drop cancelled handlers); runtime built
  manually with `shutdown_timeout(1s)`; signals watched during MCP initialization; parent-death signal checks
  `getppid()` against the fork race; group kill done right after reaping and guard disarmed (PID reuse); dev proxy gets
  an explicit environment (tests: PATH + scratch HOME; driver: allowlist incl. HOME/CODEX_HOME for Codex auth); test
  liveness treats zombies as gone; install dir includes the platform.
- Verified: all 8 new/changed stdio tests fail against the old source and pass with the fix; real Codex re-run of the
  sleep 303/120 case now leaves nothing and devbox-mcp exits with stdin open; real hello world through tunnel-client
  still works.
- LESSON: the fake's `setsid sleep &` raced the fake's own exit, so the child was still in the agent's group and got
  (correctly) killed; fakes that simulate detachment must wait until the child has actually detached.
- Remaining documented gaps (need a cgroup per agent): abrupt devbox-mcp death, and processes already orphaned out of
  the agent's tree.
