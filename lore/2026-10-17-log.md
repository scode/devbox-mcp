## 2026-10-17 17:15 — Review follow-ups: runner failures keep their cleanup result

- Working through three findings of the 2026-10-12 review that needed the user's judgment, as a stack of PRs on #33:
  failures after an agent starts lose the cleanup result (this PR), the exit watcher holds a blocking thread per turn,
  and existing state files keep loose modes. The user chose the proper fix here over reporting every runner error as
  uncertain, which would also mislabel an agent that never started.
- `process::run_agent` now returns failures after the agent started as `Ended::Failed { error, cleanup_confirmed }`: a
  stdout read error takes the same awaited cleanup as an interrupt, a failed exit watch reports cleanup unconfirmed
  (the PID can no longer be signalled safely), and a failed reap carries the cleanup result already known. A bare error
  now means only that the agent never started, which is what the session layer's mapping relies on.
- DECISION: a read error while draining the pipes after the agent is gone ends the drain the way the drain deadline
  does, instead of failing the run: the agent is already cleaned up, and all that is lost is the rest of its output.
  The alternative, a failed run with the cleanup result attached, would mark completed turns failed over unread output.
- Proved with a fake agent whose process chain is deeper than the cleanup walk's generation limit and which then
  prints a line that is not UTF-8: the run ends failed with cleanup unconfirmed (it returned a bare error before).

## 2026-10-17 17:50 — Correction: drain read errors fail the run

- The decision above to let a read error while draining end the drain quietly is reversed. The gpt-6.1-sol review of
  this change pointed out that whether the agent's exit or its unreadable line is noticed first is a matter of
  scheduling, so the same output would complete one turn and fail another, contrary to the spec text this change adds.
  A drain read error now fails the run too, with the cleanup result already known (confirmed after an exit). A test
  repeats the exit-then-bad-line case 20 times and requires a failure every time.

## 2026-10-17 18:05 — Review follow-ups: exit watching without a blocking thread

- The process runner noticed an agent's exit with a blocking `waitid` on a thread of the async runtime's blocking pool,
  held for the whole turn; interrupt cleanup needs a thread from the same pool, so with the pool full of watchers no
  interrupt could complete. It now polls a non-blocking `waitid` every 50 ms, the option the user chose over an
  event-driven pidfd (which would need tokio's `net` feature, and with it TCP listener code).
- A test with a two-thread blocking pool interrupts three hanging runs; with the old watcher it fails with the pool
  starved. LESSON: its first version hung instead of failing, because dropping the runtime waits for blocking threads
  that are stuck behind agents only the queued cleanups would kill; it now shuts the runtime down in the background and
  uses short-lived agents.
- At the user's request TODO.md gains "Event-driven exit watching" under possible future improvements.

## 2026-10-17 18:30 — Review follow-ups: tightening state and unit permissions left loose from before

- #33 made what devbox-mcp creates private, but existing files keep their modes (the live box: state directories 775,
  records and unit 664). At the user's request devbox-mcp now tightens them itself: at every start the state and
  sessions directories to 0700, the lock and each record to 0600; setup makes the unit directory private. Directories
  above them that the user owns and others can write to (`~/.config`, `~/.local/state`) are only warned about, since
  other programs share them.
- DECISION (from a planning review): records and the lock are tightened through a file descriptor, records opened
  without following symlinks, because the sessions directory used to be group-writable and a planted link would
  otherwise redirect the chmod to another file of the user. No separate ownership check: a chmod that fails is the
  refusal. The ancestor warning skips directories the user does not own, so `/` and `/tmp` never warn.
- A review found the lock was still opened following symlinks, so a link planted at the lock path redirected the
  new chmod to an unrelated file (reproduced: a 0755 file became 0600). The lock is now opened with `O_NOFOLLOW`, and
  devbox-mcp refuses to start when a link sits there; a test covers it.
